# Schedule Implementation Plan

**Goal:** Display and edit the upcoming scan order while saving only explicit next-run overrides.
**Architecture:** One sparse override table and a pure ordering function shared by the schedule read model and scheduler. Server functions validate edits; a route provides staged drag/drop and accessible move/reset controls.
**Tech Stack:** TanStack Start, React, Drizzle/PostgreSQL, Bun.
**Spec:** docs/superpowers/specs/2026-11-13-schedule-design.md

## Global constraints

Only moved/reset repository IDs are written. Overrides are consumed on successful scheduled dispatch. Preserve automatic selection, cron eligibility, cooldown and capacity constraints. Publish to main as requested, through GitHub API with signatures and required co-authors.

## Review focus

- Active or disabled repositories must not be introduced by an edit.
- Multiple manual positions and collisions must remain deterministic.
- Scheduler dispatch consumes only the selected override.
- Empty schedules and failed saves retain usable UI state.
- Custom cron repositories must not run before their due time.

## Review and verification

A fresh reviewer found repeated-move replay errors, custom-cron interference in dispatch and a save/dispatch race. All three were fixed before publication. Sparse floating sort keys preserve repeated moves without writing shifted rows; due custom schedules are handled separately; nonblocking advisory locks serialize schedule edits and scheduler ticks. Database smoke checks cover sparse save/reset, stale saves, disabled/active/custom exclusions, lock contention, distributed selection and override consumption. Unit tests cover repeated moves and automatic rank changes.
